Команда: PM, 2 Flutter-разработчика, 2 Backend-разработчика, UX/UI-дизайнер, маркетолог, тестировщик. Спринт — одна неделя.

Работаю по Scrum: каждый спринт заканчивается инкрементом, который можно показать заказчику. Цели спринтов сформулированы перед списками задач.

После двух спринтов закрыты 2 истории из 6 в Walking Skeleton — A1 (регистрация) и B1 (создать питомца). Полный сквозной поток замкнётся к концу спринта 4, когда будут готовы C1 (семья), D1 (задача), D3 (push), D2 (отметка). Семья, задачи и медицинский журнал планируются на спринты 3 и далее.

## Definition of Done

Задача считается завершённой, когда:

- код смержен в `main` через pull request с минимум одним апрувом;
- для бэк-задач — есть юнит-тесты на happy path и обработку основных ошибок;
- для пользовательских задач — QA подтвердил по чек-листу;
- для бэк-задач — обновлена OpenAPI-документация;
- для дизайн-задач — макет согласован с PM и передан в работу.

## Структура карточки на борде

ID для перекрёстных ссылок (PROD-1, BE-1, FE-1 и т.п.); название и цель; блок (продукт, дизайн, backend, Flutter, QA, маркетинг); приоритет (High/Medium/Low); связанные user stories из USM; зависимости; оценка в часах; спринт.

Колонки на борде: Backlog, To Do, In Progress, Review, Done.

## Допущения

- Стек бэка выбирается командой в день 1 спринта 1 (BE-1). По умолчанию рассматриваются Python/FastAPI или Kotlin/Spring — у команды есть опыт в обоих.
- Окружение в этих двух спринтах — только dev. Stage и prod настраиваются позже.
- Push-уведомления (FCM) и связанная инфраструктура — не в скоупе спринтов 1–2, появляются вместе с эпиком D.
- Дизайн-система готова в минимальном объёме к концу спринта 1, временные стили во Flutter допустимы.

## Порядок задач

Регистрация и вход стоят первыми по структурной зависимости: каждый следующий экран опирается на user_id, каждая запись в БД привязывается к пользователю. Auth — это самый дешёвый способ получить работающий вертикальный срез от формы на экране до записи в базе.

Профиль питомца на втором спринте идёт следующим по той же логике. Семья опирается на питомцев, задачи — на семью и питомцев, медицинский журнал — на питомцев. B-эпик первым среди «контентных» эпиков по структурным причинам, а не по приоритету для пользователя.

Дизайнер во втором спринте уже готовит вайрфреймы семьи под спринт 3, бэкенд закладывает каркас API эпика C (BE-8). Это нужно, чтобы к началу спринта 3 не упереться в простой команды.

## Риски и зависимости

Реальных рисков для двухнедельного отрезка немного, но их стоит зафиксировать:

**Bus factor дизайнера и QA.** В команде по одному человеку на каждой роли. Если дизайнер выпадает на 1–2 дня в спринт 1 — DES-3 не успевает, FE-2/FE-3 стартуют позже. Митigation: вайрфреймы DES-3 готовятся в первые два дня спринта, Flutter может начать вёрстку с временными стилями и заглушками, не дожидаясь финальных макетов. Аналогично для QA: один заболевший день в конце спринта переносит прогон auth на следующий понедельник, инкремент тогда демонстрируется в среду спринта 2, не на ревью спринта 1.

**Зависимость FE от BE-3 (Auth API).** Если бэк-эндпоинты не готовы к среде спринта 1 — Flutter не сможет интегрироваться. Митigation: API-контракт фиксируется в формате OpenAPI в день 1 (часть BE-1 + начало BE-3), Flutter работает с моком, переключается на реальный бэк за полдня.

**Доступность заказчика для PROD-1.** Уточнение четырёх открытых вопросов требует встречи с Сергеем. Если она не состоится в первые два дня спринта 1 — продукт принимает временные решения и фиксирует их как допущения, чтобы не блокировать команду. Высокий риск только для офлайн-сценариев (вопрос 3) — это влияет на архитектуру синхронизации и его стоит закрыть в первую очередь.

**Стек бэка не зафиксирован.** Решение принимается командой в день 1 (BE-1). Затягивание выбора больше чем на полдня съедает остаток BE-1 и сдвигает BE-3 в среду–четверг — auth не успевает к QA. Митigation: PM модерирует встречу выбора стека в первое утро, ограничение по времени — 1 час.

Все остальные риски — общекомандные (внешний инцидент, болезнь нескольких человек разом) — стандартные для любого Scrum-проекта и в этом плане отдельно не разбираются.
